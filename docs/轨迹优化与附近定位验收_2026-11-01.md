## 优化与取消的真实边界

- 原始 YAstar 路径先检查精确首末坐标和完整车身扫掠；候选曲线的每条输出边使用同一标准检查。未知格、致命障碍和地图越界仍拒绝，不靠缩小车身或放宽守卫通过。
- 优化失败、碰撞、点数、长度、偏离或预算超限会明确记录原因并回退；**外部取消则停止整个规划请求，不回退继续返回路径**。
- 默认合作式优化预算 30 ms、12 控制点、1200 输出点；一次 Eigen 求解不能抢占，整条规划请求不具有 30 ms 硬实时保证。
- 输出仍是普通 Nav2 几何 Path，没有按分段时间跟踪速度/加速度的控制保证。洞内仍由现有 BT 生成并跟踪直线轴线，不直接使用优化曲线。
- 标准非扩展插件仍兼容，但只在调用前后判断取消；本地 server 与 rclcpp_action 的明确版本相关，升级 Nav2/ROS 时需重新审查。

TDT 求解函数体的来源、SHA、MIT 授权和技术限制见《算法与边界说明.md》；本地 server 有独立 `UPSTREAM.md` 和原 Apache-2.0 许可。

## 定位和实际出生位姿

第一版按用户确认，仅处理已知出生区域附近摆放误差。默认实体出生 `(-5.3,3,0.3),yaw=-π/2`，地图 base_footprint 初猜 `(-5.3,3,0),yaw=-π/2`，二者不再共用一个值。Point-LIO 仍提供相对里程计，地图位姿由先验点云匹配得到，没有将 Gazebo 真值送入生产定位。

GICP 需连续健康配准，源时间和接收时效也须合格。默认连续 3 次，配准质量阈值是当前场景的调试初值，不是全局位置唯一性或安全证明；`mean_gicp_error` 是协方差加权代价，不是米制 RMSE。源时间/时钟回退、手动初值重置或质量失败会撤销可信。

`route_status.home_pose` 在第一次准备发送任务时记录真实估计位姿；重复任务不覆盖，时钟回退清空并立即对外发布（含回退到 0）。记录不落盘、不执行返航。固定三点仍是原 map 坐标，不会随出生点平移或自动交换隧道入口。

**新增门控只约束 startup_navigation 的固定路线**；直接 RViz/action 目标不会自动经过该门控，也没有新增运行中定位异常强制停车。GT 不依赖 GICP，建图模式不创建自动任务。

## 失败及仍保留的问题

1. `optimized_route` 首次洞内触发中心线偏差保护并 ABORTED，输入当段新鲜；map 与 raw 存在厘米级差异，洞内执行原专用轴线。未改变守卫的 `optimized_retry` 两路线成功；不能认定根因已消失。
2. `ground_truth_start` 首次开启优化在多点规划阶段被 goal 完整车身碰撞检查拒绝，机器人尚未驶入隧道。关闭优化一次成功、原开优化配置复测一次成功。旧/新接口末点朝向一致，后续段终点检查在该段优化之前；没有充分现场 costmap 证据唯一归因，保留为间歇问题，不写成优化引起或已修好。
3. 两次观察器错误（UUID 的 numpy uint8 序列化、nanoseconds 属性误作函数）分别保留原记录并在新目录重验；不把不完整记录当最终验收。前者曾跳过自动清理，随后按专属 partition 回收，再确认无残留。
4. 源/时钟回退和手动定位重置未做整场仿真实物重置验证；已检查实现并有纯逻辑回归。真实 Gazebo 的规划取消发生在很短规划结束后行进阶段；耗时搜索取消由 adapter/server 受控测试覆盖，不冒称所有实场景取消均已统计。
5. 保留原有长时扫描/定位稳定性、里程计速度估算与 shutdown traceback 待办；这些不因本轮测试通过而关闭。
6. 待后续验收：同起点大量开关对照、真机附近摆放阈值、小电脑 CPU/时延、MCU 协议、实际返航/等待再出发。当前没有执行这些功能。

本轮实例均已按专属 partition 清理，最终只读进程核对为空。没有全局终止其他进程、删除 build/install、提交或推送。
