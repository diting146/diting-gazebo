## 目标机重编译与运行核对

- [ ] 先核对系统、ROS Humble、架构和工具链；确认 Livox SDK 对应架构可加载。当前源内有 amd64/arm64 库，不代表目标机已经验证。
- [ ] 明确当前工程有 **15 个跨两层的同名包**。以两层 `--base-paths src` 构建，不能从根目录无边界扫描整个工程。
- [ ] 若按**现有完整工程布局继续运行仿真**，安装其 package.xml 声明的依赖，按以下顺序在目标机执行。此顺序不是未来真机最小依赖方案，本轮未执行：

```bash
source /opt/ros/humble/setup.bash
export NAV_WS=/目标机/实际工程路径
cd "$NAV_WS"
colcon build --base-paths src --symlink-install --cmake-args -DCMAKE_BUILD_TYPE=Release
source "$NAV_WS/install/setup.bash"
cd "$NAV_WS/sentry_nav"
colcon build --base-paths src --symlink-install --cmake-args -DCMAKE_BUILD_TYPE=Release
source "$NAV_WS/source_all.bash"
```

- [ ] 检查实际包路径：后加载的 overlay 优先，避免误用另一份控制器/定位配置。
- [ ] 检查地图、先验点云、SDK、动态库与 PCD 输出目录均指向新位置，不能依赖原电脑 `/home/hui/...` 的绝对路径。
- [ ] 检查雷达真实 IP 与接口、点时间/IMU 单位、TF 发布方；真机使用 `use_sim_time=false`，不启动 Gazebo `/clock`、假里程计与假 MCU 网关。
- [ ] 优先让开发电脑远程运行 RViz，小电脑只运行必要节点。先核实话题发现、QoS、TF 与时钟；不默认把当前 UDPv4 规避配置当所有设备最优设置。
- [ ] 记录 CPU、内存、温度、扫描延迟、控制周期、磁盘增长和路线耗时；目标机线程数和通过速度均须实测，不能照搬桌面机成绩。

真机最小运行集合可复用定位、YAstar、控制器、隧道 BT、速度转换与必要 TF；需补真实传感器和底盘驱动。当前 bringup 的依赖声明仍含 Gazebo/RViz 等，旧 reality launch 又使用旧导航参数。**本轮不删除依赖、不提供未经验证的真机启动命令**，后续在已确认硬件边界下单独整理。

## 协议未定时，先约定哪些接口

- [ ] 明确速度命令只有一个有效来源；计划从 `/sentry_robot1/cmd_vel_chassis` 接入真实驱动，不重复做地图系/底盘系转换。
- [ ] 双方确认 ROS 坐标：底盘 x 前、y 左、z 上；平移 m/s、角速度 rad/s；yaw 正方向、零点、范围与是否连续。以上为建议约定，必须用实车单轴动作确认。
- [ ] 确认实测速度/轮速、底盘 yaw、云台相对角、模式/故障等反馈的坐标、单位、采样时间和有效标志。
- [ ] 明确 LIO odometry 与原始底盘反馈分开；同一条 TF 只能有一个发布方，主控驱动不能抢占现有定位 TF。
- [ ] 明确上位机命令过期处理和**主控独立断流停车**责任；程序退出或拔线仍须停车。超时数值依据命令周期、最坏延迟和制动能力确定，不照抄仿真值。
- [ ] 等待双方确定：实际接口、波特率/总线速率、帧结构、消息 ID、字节序/比例、CRC、序号/时钟、握手与故障恢复。本清单不预设任何 packet 格式。

准备完成的判据是：源码与资源完整、目标设备信息齐全、现有仿真能在目标机重建验证、真实 ROS 接口责任明确。真实底盘协议和上车验收仍是后续工作。

分层构建还要分清当前shell：构建根工作区前只加载ROS基础环境；构建overlay前加载ROS和已完成的根install。不要先source_all再回根目录构建，否则colcon可能把overlay记成根工作区的underlay，形成错误覆盖顺序。新终端source_all后，使用ros2 pkg prefix核实关键导航包实际来自sentry_nav/install。
