# 扫描接收缓存专项修复

日期：2026-10-31。工程：`/home/hui/diting-gazebo-feat-sentry-nav-simulation`。

## 本轮范围

按“一个一个修复”先处理扫描传输稳定性。正式运行配置只修改 `sentry_nav/src/sentry_sim_bringup/config/fastdds_udp.xml`，在 UDPv4 transport descriptor 增加：

```xml
<receiveBufferSize>212992</receiveBufferSize>
```

已对 `sentry_sim_bringup` 增量安装，源文件和安装副本逐字一致，XML 可解析。没有修改系统 sysctl、发送缓存、点云频率、扫描超时阈值、速度、控制器、行为树或定位实现；旧工作区未修改。测试程序和证据保存在本审计目录，未加入正式启动链路。没有提交或推送 Git。

## 原因与证据

当前主机原 UDP socket 接收容量为 212992 B。单帧原始点云数据为 368640 B，经过网络传输存在分片和突发到达，接收队列不足会丢弃部分数据报，完整点云无法交付；扫描因此可能缺帧。显式请求 SO_RCVBUF 后，Linux 的 socket 记账容量在本机实测为 425984 B。该值必须运行时确认，不能仅凭配置文件或启动无报错判断。

这是一项有对照证据的接收溢出修复，并不唯一解释全部历史异常：之前出现过 MessageFilter queuefull 和约 1.9 s 扫描空档，尚未在转换器内部建立每次异常与 socket 丢包的对应关系。

## 对照一：真实场景

两轮使用相同安装库、同一出生点、LIO/YAstar、相同固定三点路线，唯一候选配置变化是接收缓存。两轮路线均成功。

| 观察指标（仿真时间 > 5 s） | 原配置 baseline_01 | 候选 buffer_212992_01 |
| --- | ---: | ---: |
| 最大扫描到达间隔（墙钟 s） | 0.2783 | 0.1737 |
| 最大观测扫描年龄（仿真 s） | 0.066 | 0.030 |
| 扫描间隔 p95（墙钟 s） | 0.1337 | 0.1380 |
| 扫描年龄中位数（仿真 s） | 0.015 | 0.016 |

不能把不同订阅者的云/扫描缺配对直接算成转换器丢帧。候选轮稳态 516 帧云与 516 帧扫描 stamp 全配对；原轮存在双方各自未配对的帧。UDP 新增丢包按进程存活时间归一后，多数关键进程下降，Point-LIO 未改善；完整场景仍有接收丢包。因此结论是本轮长尾改善，不能写成所有分位延迟降低或整套链路零丢包。

证据：两 case 的 `扫描时间分析.json`、`UDP接收归一分析.json`，以及本目录 `接收缓存对照结论.md`。

## 对照二：受控跨进程负载

publisher、实际 overlay converter、observer 分别独立运行；相同库、相同负载定义 SHA，各自保留发送端原始时间戳，未重新盖戳。45 s 测量，点云正常 10 Hz，含相同 2 s 的 20 Hz 突发；单帧数据 368640 B。两条动态 TF 标称 100 Hz，但实际受 Python 发送调度影响约 79 Hz，不能标为已达到 100 Hz。两轮观察到的 TF 序列完整。

## 使用及回退

新终端照常加载 `source_all.bash` 并正常启动仿真即可，不需要增加节点或命令行参数。必须正常关闭旧实例并重启，新 socket 才采用新容量。若调用者显式指定自己的 DDS profile，环境脚本会保留覆盖值；该情形需自行检查 profile 和实际 socket 容量。

回退时移除该字段，重新安装 `sentry_sim_bringup` 后正常重启。修改前文件在 `修改前/sentry_nav/src/sentry_sim_bringup/config/fastdds_udp.xml`；不需要还原任何系统参数。本项提高接收队列容量上限，未新增计算模块；迁移到小电脑时仍需验证其内核限制、实际容量与负载下时效。
