审计日期：2026-10-31。目标工程：`/home/hui/diting-gazebo-feat-sentry-nav-simulation`。本说明只新增在文档目录；没有修改被审计工程的源代码、配置或构建产物，没有构建、启动节点或连接实际主控板。路线优化的最终实测参数以本轮主报告为准，本篇负责部署与通信边界。

## 1. 结论与当前能提前完成的事

现有代码具备可复用的导航、定位、点云处理、隧道行为树基础，但**当前唯一双车仿真入口不是可以直接控制真车的入口**。它仍会生成 Gazebo 机器人、连接 Gazebo 传感器，并启动假的 MCU 速度网关。协议未确定时，可以先固定 ROS 侧速度与反馈契约、TF 发布责任、时间同步方案、进程清单和部署依赖；不能把这些准备写成“串口已经接好”。

工程两层源码中没有找到真实 `serialdriver`、串口读写节点或底盘通信专用消息；`sim_serial_gateway` 与 `sim_lio_gateway` 都没有打开设备、发送字节帧或解析 MCU 反馈。它们只是把 ROS `Twist` 转发给 `ros_gz_bridge`，再交给 Gazebo 插件。搜索本地常见候选目录也没有找到可确认的现成底盘驱动；`/home/hui/work/ros_ws` 有 RMOSS 固定包工具，但它没有在当前工程里形成真实底盘链路。

因此，本次**没有可列出的“当前底盘线缆协议”**。帧头、字节序、字段长度、CRC、波特率等全部待双方确定，不从仿真节点名称或第三方工具猜测。

真实底盘反馈不能直接发布到当前 `/sentry_robot1/odometry` 覆盖 LIO 输出，也不能同时发布同一个 `odom → base_footprint` TF。建议把原始轮速/底盘里程计保留成独立接口，今后是否融合另行决定。

当前默认 LIO 模式的导航 odometry 链是 `Point-LIO → loam_interface → sensor_scan_generation → /sentry_robot1/odometry`，不依赖主控轮速。它的位姿/速度不能称为“已收到真实底盘反馈”；当前 velocity_smoother 配置为 `OPEN_LOOP`，已有 odometry 订阅也不等于它正在用主控实测速率做速度闭环。

## 3. 当前控制链：通信驱动应该接在哪里

默认命名空间为 `sentry_robot1`，当前链路为：

```text
Nav2 FollowPath / 行为节点
  → /sentry_robot1/cmd_vel_controller
  → Nav2 velocity_smoother
  → /sentry_robot1/cmd_vel_nav2_result
  → fake_vel_transform
  → /sentry_robot1/cmd_vel_chassis
  → sim_lio_gateway（仿真）
  → /sentry_robot1/cmd_vel
  → ros_gz_bridge → Gazebo MecanumDrive2
```

部分 BT 直接产生准备阶段的速度，同样经既有速度入口和转换链进入底盘。后续硬件驱动的最小接入位置建议是**订阅 `/sentry_robot1/cmd_vel_chassis`，发送主控命令**；替换后半段，保留上层导航、规划器和隧道逻辑。这里是接口方案，尚未实现真实驱动。

当前 `fake_vel_transform` 的 `robot_base_frame` 经配置为 `sentry_robot1/chassis`，伪参考系为 `sentry_robot1/gimbal_yaw_fake`。它按 odometry 的 yaw 把平移速度旋转到底盘方向，角速度输出为输入角速度加 `cmd_spin`。**主控若再把这组速度当地图系/云台系旋转一次，会造成重复变换。**

现有 ROS 命令类型是 `geometry_msgs/msg/Twist`，没有 header、时间戳和 frame_id。因此协议层不能从消息里自动推断坐标系或发送时刻，应在接口契约里固定坐标，并在驱动接收时记录单调时钟；是否增加序号或下发有效期由协议设计决定。

## 4. 可以先确定的 ROS 侧契约（建议草案，不是已实现协议）

| 接口 | 第一版建议约定 | 仍需双方确认 |
|---|---|---|
| 速度命令 | 保留 `Twist`：`linear.x/y` 为底盘坐标的前/左速度，单位 m/s；`angular.z` 逆时针为正，单位 rad/s；不使用其余轴 | 底盘机械前向、主控现有轴正负；是否全向；是否主控接受速度而非位置/电机转速 |
| 速度上限 | 上位机做导航限速，主控做独立物理上限和斜坡/制动约束 | 最大线/角速度、加减速度、斜加速与负载限制；不能把仿真 0.8/1.0 m/s 当真车已验证值 |
| 控制来源 | 同一时刻只有一个有效底盘控制源；自动/遥控/急停有明确优先级 | 接管信号来自遥控器、主控还是上位机；切换确认与恢复条件 |
| 命令有效期 | 驱动使用 steady/monotonic 时间判断新鲜度；过期清零；主控也必须独立判断链路断流 | 下发频率、最大延时/抖动、丢包容限、超时值；必须保证程序崩溃/USB 断开仍可停车 |
| 实测速度反馈 | 至少返回实际 vx/vy/wz 或可换算的轮速，带采样时间/序号和有效标志 | 坐标系、量程、协方差/精度、反馈频率、轮速换算责任 |
| 底盘朝向 | 需要与当前定位/云台 TF 设计一致的底盘 yaw；不要把电机编码器角或云台相对角当全局 yaw | yaw 的来源、零点、连续/±π、漂移、上电重置、是否只是相对增量 |
| 云台反馈 | 相对底盘的 yaw 编码器角，单位 rad，带真实采样时间；若发布 JointState，名称与 TF 一致 | 编码器零位、方向、绕圈、pitch、安装变换、更新率 |
| 模式/健康状态 | 收到数据与允许运动分别表达；至少可区分自动、手动、急停、驱动故障、断链 | 哪一侧拥有最终使能权，复位与故障解除规则 |
| 原始底盘里程计 | 建议独立话题，如命名空间下 `chassis/odometry_raw`；不抢占当前 LIO odometry/TF | 只是反馈监测，还是未来融合输入；本轮不新增融合 |
| 通信状态 | 序号、接收龄期、错误/丢包计数和主控在线状态可以在设计时列出 | ROS 消息选型与硬件协议字段尚未定，不为这些字段另建功能 |

以上单位/坐标是建议的 ROS 层目标契约；必须用低速单轴测试确认主控实际映射，不能仅依赖字段名称。

### 上位机与主控的责任边界

上位机负责定位、地图、全局规划、局部跟踪、隧道流程、生成速度命令及日志；驱动负责有限值/范围检查、单位坐标映射、封包解包、序号与时间记录、连接错误和反馈发布。主控负责轮速闭环、电机执行、物理限幅、控制模式仲裁、独立命令超时停车、急停及驱动故障处理。底盘板断流停车不应依赖上位机“最后再发一帧零速度”。

仿真中 `fake_vel_transform` 的输入断流阈值为 0.5 秒，仿真网关默认 200 ms，且待机角速度可以非零；这些是现状，**不是建议直接照抄的真机安全值**。实际值须根据发送周期、最坏延时和制动距离确定；真机失联默认停止包括角速度的建议需要在协议层明确，不能把“自旋待机”隐式当失联策略。

### 协议必须等双方确认的清单

传输介质（USB CDC/UART/CAN/以太网）、设备电气规格、速率/串口参数或 CAN ID；帧头/尾、版本号、包长与消息 ID；整数/浮点和字节序、比例因子与量程；CRC/校验覆盖范围、转义与粘包拆包；命令/反馈序号和采样时刻；心跳、重复/过期命令处理与超时；启动握手、模式/急停、故障码及恢复；主控重启后计时/零点重置规则。此处仅列需要做决定的项目，不指定任何 wire 字节格式。

## 5. TF 和时间：必须提前分清谁发布

在保留当前 LIO 导航设计时，建议责任表为：

| 变换/数据 | 当前来源 | 真机方案与约束 |
|---|---|---|
| `map → odom` | small_gicp 重定位；建图模式另有静态单位变换 | 保留定位端唯一发布；导航模式不能再同时启动静态 map→odom |
| `odom → base_footprint` | sensor_scan_generation 根据 LIO 输出产生 | 若保留此设计由定位链唯一发布；MCU 原始轮速 odom 不同时发布这条边 |
| `base_footprint → chassis` | 仿真静态变换，z=0.076 m | 用实际底盘基准与离地高度确认，避免把仿真地面基准直接照搬 |
| `chassis → gimbal_yaw_odom → gimbal_yaw` | 仿真 sentry_gimbal_tf + JointState | 使用真实关节反馈与标定外参；明确由 robot_state_publisher 或专用节点中的一方发布 |
| `gimbal_yaw → lidar_link` | 仿真安装外参 | 根据真实雷达安装测量/标定；若雷达实际固定在底盘，整条父子关系应重新设计 |
| `chassis → gimbal_yaw_fake` | fake_vel_transform | 当前只是导航稳定方向参考系，不是机械关节，不应由 MCU 当作物理关节反馈 |

TF 的 parent/child、namespace、零点和时间戳要作为接口文档的一部分。真实反馈必须用**采样时刻**，不能统一用转发到上位机的当前时间掩盖延迟。真机全链 `use_sim_time=false`，不需要 `/clock`；驱动 watchdog 仍用单调时间。雷达、IMU、关节反馈与主机时钟如何同步待硬件确认；多台上位机使用时再确定统一时间同步方式。

本轮扫描修复代码已给 `sentry_gimbal_tf` 增加 `max_publish_rate_hz`，默认 **100 Hz**，按 JointState 源时间戳丢弃中间样本，所发布的角度与非零时间戳仍取同一条输入，不使用定时器重播；零时间戳仍沿用原有当前时间回退逻辑，源时钟回退后重新开始间隔。它限制的是动态 TF 转发频率，不修改 Gazebo 原 JointState 发布频率，也不是给未来 MCU 固定了 100 Hz 协议。`0` 可保持不限制；实际扫描改善与整条路线验收结果见本轮主报告。[代码位置](/home/hui/diting-gazebo-feat-sentry-nav-simulation/sentry_nav/src/sentry_sim_bringup/sentry_sim_bringup/sentry_gimbal_tf.py:112)

当前 small_gicp 会把 `map→odom` 的时间设为最近扫描时间加 0.1 秒，这是现有定位实现的时间补偿，不等于 MCU 可以随意前移反馈时间戳。

## 6. 小电脑部署：先确认运行目标

小电脑型号、CPU 架构、内存、系统、雷达型号和硬件接口目前未知，因此不能承诺帧率、CPU 占用或真机通行速度。优先记录 `uname -m`、系统版本、CPU 核心数/频率、内存与磁盘、网卡/USB/CAN 设备、电源/散热，以及雷达和 IMU 的型号、安装方式及数据率。

两种部署目标需要区分：

1. **搬过去继续跑同一个 Gazebo 仿真**：完整保留当前两层工程；依赖 Gazebo Fortress、渲染及桥接。小电脑无 GPU 时仿真实时率可能显著变化，不能把仿真耗时直接当真车耗时。
2. **小电脑直接上车**：运行真实雷达/IMU、定位、Nav2、YAstar、控制器、隧道 BT 和硬件通信，排除 Gazebo、手动车和真值替身。当前缺少把这些模块按当前配置串起的独立硬件入口与 MCU 驱动，本次只说明边界，不修改入口。

### 推荐的最小运行组成

真实传感器驱动（如果仍用 MID360 则为现有 livox_ros_driver2）、Point-LIO、loam_interface、sensor_scan_generation、small_gicp_relocalization、pointcloud_to_laserscan、Nav2 运行节点、tdt_yastar_planner、pb_omni_pid_pursuit_controller、fake_vel_transform、sentry_tunnel_bt、经过确认的 TF 发布方，以及未来硬件驱动。固定三点任务若保留则增加当前任务节点。地图 YAML/图像与先验 PCD 是同一场地配套数据。

这是一份**运行模块清单，不是目前可直接执行的最小 colcon 命令**：`sentry_sim_bringup/package.xml` 仍声明 Gazebo 和 RViz 依赖；原 `pb2025_nav_bringup` 还声明建图/地形分析等依赖。直接 `rosdep install` 会按包声明安装依赖，不能据此认定这些节点全部会运行，也不能在未整理 manifest/launch 前承诺完全去除 Gazebo 依赖。

RViz 可留在开发电脑，经网络查看；车载端不必启动 GUI。日志和 rosbag 应设置保存目录及磁盘预算，避免把全量点云长期写入小容量盘。是否使用 systemd/容器、是否开机自启动，等手动硬件验证完成后再选，本轮不新增。

### 当前的构建边界与迁移风险

| 已核实的事实 | 迁移时的处理建议 |

## 7. 旧真机入口可以参考哪些，不能直接沿用哪些

现有 `rm_navigation_reality_launch.py` 确实会启动 livox_ros_driver2，默认 `use_sim_time=false`，加载 reality 地图/PCD/参数，并启动原导航链。但它不是最近仿真工作的硬件版：

- 默认世界为 `rmul_2024`，真实地图、先验点云与初值不是当前场地硬件标定。
- reality 参数仍为 Theta*，普通目标 0.15 m，控制上限 ±2.5 m/s，`init_spin_speed=3.14`；没有当前 FollowPathTunnel/双目标检查器与三点隧道任务的完整配置。
- 其机器人参考系为 `gimbal_yaw/front_mid360`，现仿真在 Nav2/速度转换中使用 `chassis/gimbal_yaw_fake` 等关系，不能混用。
- reality 扫描高度为 -0.5～6.0 m、强度范围 0.1～2.0；现仿真 0～0.15 m 是基于仿真安装高度处理隧道顶板的结果，二者都不能未经真实点云核实直接作为新车配置。
- reality 的 Point-LIO 雷达格式、点时间、IMU 单位/外参与仿真不同，这是接硬件应核对的内容，不是只把 use_sim_time 改为 false。
- `use_robot_state_pub=false`，默认依赖外部完整机器人 TF。工程的 robot_description 配置提到 `serial/gimbal_joint_state`，但这只是预期输入话题，不证明串口驱动已经存在。

## 9. 后续硬件验收顺序（计划，不代表已完成）

1. 上位机只接收反馈、底盘禁止使能：检查拆包、序号、采样时间、单位和轴向；验证雷达/IMU/关节 TF 正确且唯一。
2. 低速单轴和单角速度：检查前/后/左/右/转向，核实主控不会重复旋转坐标；检查实际速度与目标速度。
3. 验证切手动、急停、进程退出、驱动失联、物理拔线、主控重启时的独立停车；不依赖最后零速度帧。
4. 先普通空地导航，再入口对齐，最后低速隧道；在真实制动和定位延时测量之后决定提速，沿用有界失败停车而不是绕过保护。
5. 用目标机负载、实际反馈、整条路线耗时与重复通过记录验收；仿真成功不替代真机通过，也不替代协议验收。
