# 扫描超时审计与限定修复（2026-10-31）

本记录区分已证实的消息积压/负载问题与尚未确定的历史偶发超时根因。不会把数轮无复现写成根治。

## 1. 当前实际扫描链路

`Gazebo GPU LiDAR → ros_gz_bridge → /sentry_robot1/points_raw → pointcloud_to_laserscan → /sentry_robot1/obstacle_scan → Nav2 costmap / TunnelPassage`

- LiDAR 源为 10 Hz、水平 360 × 垂直 32 点。来源：[model.sdf](/home/hui/diting-gazebo-feat-sentry-nav-simulation/sentry_nav/src/sentry_sim_bringup/models/sentry_rm25/model.sdf:378)。
- 桥接主题及方向由 [sentry_bridge.yaml.in](/home/hui/diting-gazebo-feat-sentry-nav-simulation/sentry_nav/src/sentry_sim_bringup/config/sentry_bridge.yaml.in:6) 定义。
- LIO launch 直接把 `points_raw` 接到扫描转换器，未经过 Point-LIO、地形图或先验点云：[lio_navigation_launch.py](/home/hui/diting-gazebo-feat-sentry-nav-simulation/sentry_nav/src/sentry_sim_bringup/launch/lio_navigation_launch.py:178)。Point-LIO 的 livox_cloud_adapter 是同一原始主题的另一分支。
- 转换器以点云源时间戳查 TF；输出复制该时间戳，转换至 `gimbal_yaw_fake`。高度过滤仍为 0.0–0.15 m，不是超时参数。
- 精确时间 TF 链依赖 `lidar_link → gimbal_yaw → gimbal_yaw_odom → chassis → gimbal_yaw_fake`，其中云台角 TF 与 fake frame TF 为动态边。

## 2. 历史超时能证明什么

历史 `optimized_04_v3` 中，仿真时间 29.002 秒：

| 项目 | 源时间戳年龄 | 距最后收到消息的稳态时间 |
|---|---:|---:|
| odometry | 0.102 s | 0.0405 s |
| obstacle_scan | 0.802 s | 0.7905 s |

此时 BT 的停车保护正确触发，随后有界重试成功。证据：[navigation.log](/home/hui/文档/ChatGPT/导航仿真/过洞流程优化_2026-10-30/optimized_04_v3/navigation.log:288)。另外两份较早完整路线日志也出现相似 0.8 s 扫描空档。

这证明 BT 确实约 0.8 s 未接收新扫描，且当时里程计仍在更新。无法仅凭现有日志区分：GPU 源暂停、Gazebo/ROS 传输、转换器输入读者、等待 TF，或输出读者瞬时停顿。五秒一级的 adapter 计数不能排除局部 0.8 s 中断。

后续 costmap 的 “earlier than all the data in the transform cache” 发生于其他时刻，不能直接认作这次 29.002 秒超时的原因。转换器历史无 `Transform failure` / MessageFilter 掉帧日志。Humble 的 MessageFilter 自带节流掉帧日志，不能说完全没有日志；但是尚未解锁的 TF 等待不会立即形成掉帧日志。

## 3. 本轮未修改前观测

外部观察脚本记录 cloud / scan 源时间戳和稳态到达时间、TF、joint_states，不增加生产节点。证据分别保存到各测试目录 `sensor_timing.jsonl` 与 `扫描时间分析.json`。

| 观测 | baseline_01 | approach_045 |
|---|---:|---:|
| 原始 cloud 数 | 440 | 425 |
| scan 数 | 425 | 414 |
| cloud → scan 匹配样本的中位到达差 | 1.77 ms | 1.31 ms |
| cloud → scan 匹配样本的最大到达差 | 10.67 ms | 10.66 ms |
| scan 稳态到达间隔最大值（仿真时间 > 5 s） | 0.310 s | 0.316 s |
| scan 源时间戳间隔最大值 | 0.2 s | 0.2 s |
| scan 乱序 | 0 | 0 |

没有复现 0.8 s。观察器是独立 best-effort 读者，部分它未收到的 cloud 对应 scan 仍存在，因此 “观察器漏收” 不能直接算成“转换器丢帧”。TF 时间覆盖统计也只能作为观察器覆盖估计，不代表转换器内部 Buffer 的实际等待延迟。

`approach_045` 的 joint_states 实际接近 1000 Hz，33,056 条消息、常见源时间间隔 1 ms。现有 sentry_gimbal_tf 每条都发布动态 TF，显著高于 10 Hz LiDAR 所需的采样密度，形成可证实的冗余发布负载。这个现象不等同于历史超时的唯一原因。

## 4. 针对积压的可控对照

测试脚本：[扫描TF积压对照.py](/home/hui/文档/ChatGPT/导航仿真/路线优化与小电脑部署审计_2026-10-31/方法/扫描TF积压对照.py)。正式结果：[结果.json](/home/hui/文档/ChatGPT/导航仿真/路线优化与小电脑部署审计_2026-10-31/scan_queue_control_depth100/结果.json)。

独立 DDS 域 224，仅启动两个转换器与合成发布器：保持 10 Hz cloud，动态 TF 正常 → 暂停 1.2 s → 仅恢复当前时间 TF。点云源时间戳不改；恢复后 TF 插值使待处理点云可转换。对照相同二进制、queue_size 22 / 3；观察器 depth 100 完整接收回放突发。

| 指标 | queue 22 | queue 3 |
|---|---:|---:|
| TF 恢复后回放的暂停期旧帧 | 12 | 3 |
| 回放旧帧最大源年龄 | 1.170 s | 0.262 s |
| 恢复后第一帧新扫描到达时间 | 0.0453 s | 0.0454 s |

TF 待处理帧可以乱序解锁，大队列还会回放旧时间戳。此对照直接证明较小队列能限制本场景的旧数据回放，不增加恢复到新帧的时间。它不意味着暂停 1.2 s 期间能持续获得扫描，更不意味着应该放宽 0.8 s 保护。故障注入节点均由脚本 finally 清理，只涉及自己的 PID。

队列来源：[PointCloudToLaserScanNode 构造函数](/home/hui/diting-gazebo-feat-sentry-nav-simulation/sentry_nav/src/pb2025_sentry_nav/pointcloud_to_laserscan/src/pointcloud_to_laserscan_node.cpp:63) 默认使用硬件并发数，本机为 22；同一 input_queue_size 同时控制输入 DDS 与 TF MessageFilter 深度（90、124 行）。未配置时 10 Hz 可积约 2.2 s，不符合优先使用新观测的需求。

## 5. 本轮限定修复

1. 两份仿真 YAML 显式 `pointcloud_to_laserscan.queue_size: 3`（由主任务统一实施），限制实时障碍链 TF 队列积压；不修改 converter C++。
2. [sentry_gimbal_tf.py](/home/hui/diting-gazebo-feat-sentry-nav-simulation/sentry_nav/src/sentry_sim_bringup/sentry_sim_bringup/sentry_gimbal_tf.py:112) 默认 `max_publish_rate_hz=100.0`，在收到 joint state 时按原始源时间戳限频，只跳过中间样本，不定时器重发、不重盖新时间。首帧及源时间回退立即发布；0 表示不限制；负值/非有限配置拒绝。
3. [ScanStampGate](/home/hui/diting-gazebo-feat-sentry-nav-simulation/sentry_nav/src/sentry_tunnel_bt/include/sentry_tunnel_bt/tunnel_geometry.hpp:19) 与 [扫描订阅回调](/home/hui/diting-gazebo-feat-sentry-nav-simulation/sentry_nav/src/sentry_tunnel_bt/src/tunnel_passage.cpp:174) 保持当前 ROS 时间周期内最新的源 stamp，拒绝迟到旧帧和重复帧覆盖缓存；时间回退重置周期。未把旧数据改为当前时间，也不通过回放延长缓存收到时间。
4. 保留现有 TF、里程计、扫描新鲜度保护、停车、取消和有界重试；`data_timeout=0.8` 不变。

新增 9 项回归验证原 stamp / 角度保留、1000 Hz → 100 Hz、首帧、时间回退、不限频、缺少 joint、零 stamp 兼容、非法参数。日志：[gimbal_tf_regression.log](/home/hui/文档/ChatGPT/导航仿真/路线优化与小电脑部署审计_2026-10-31/gimbal_tf_regression.log)。完整仿真最终证据由主任务汇总，不能用单节点测试替代实际通过隧道验收。

## 6. 尚待确认及复发时取证

- 本轮完成的是抗积压与减少明确的冗余 TF 发布。历史偶发扫描中断的唯一根因尚未确定。
- 若复发，按相同源 stamp 对齐原始 cloud、scan、两个动态 TF、joint state 的 steady 到达。若 cloud 仍连续而 scan 停止，继续定位精确 TF 等待与转换器读者；若两者都停，往桥接前和源传感器追。
- 记录真实 publisher QoS。桥接 YAML 的 `qos_reliability` 字段不代表本机 ros_gz_bridge 一定使用它；本机 0.244.26 的 BridgeConfig 头文件无此字段。best-effort 读者可兼容 reliable publisher，不能仅据 YAML 或旧 RViz QoS 警告判断整条导航链不兼容。
- 小电脑评估应按真实传感器频率、TF 发布频率和所有节点同时工作时的负载测试；100 Hz TF 限频不减少原始 joint_states 传输/其他消费者的回调负载。
- 本轮已防止迟到旧扫描覆盖更新缓存；转换器内部等待故障本身尚未根治。不要用放宽扫描超时、把旧帧改为当前时间、TF 定时重发旧角度去隐藏中断。

- 同窗口 cloud 连续 18 帧、joint state 1806 帧、TF 337 条，故不是源雷达整体停摆。
- 转换器自身 [navigation.log](/home/hui/文档/ChatGPT/导航仿真/路线优化与小电脑部署审计_2026-10-31/rolling_trial_01/navigation.log:329) 明确出现 MessageFilter queue-full，丢弃源时间 32.100 s 的 lidar_link 点云，证明点云到达转换器但卡在 TF 过滤等待，不能简单归因观察器漏收。
- 31.5–34.5 s 窗口独立观察器看见云台动态 TF 最大源间隔 0.04 s / 到达间隔 0.058 s，fake-frame 动态 TF 最大源间隔 0.04 s / 到达间隔 0.066 s。TF 发布源连续不等于转换器内部 Buffer 已收到并成功解锁等待，还需要内部取证。

- 实际 endpoint QoS 已记录：points_raw 与 joint_states 的桥接 publisher 为 RELIABLE，obstacle_scan publisher 为 BEST_EFFORT。相应读者兼容，这不是 QoS 不兼容阻断。
- 本轮云台动态 TF 源采样间隔中位、p95、p99 均 0.010 s，100 Hz 限频确已生效，没有把缺失扫描源时间戳伪装为新数据。

下一步应在同一个转换器内部检查源时间精确 TF 的 canTransform 结果与 MessageFilter 是否仍不解锁，区分 Buffer 输入缺失和异步等待状态问题。Humble 本机 `registerFailureCallback` 被 `#if 0` 禁用，不能直接依赖该 API。主任务在继续排查，本文后续数据以最终汇总为准。


## 8. 限定内部诊断收尾

本机实际加载的 `pointcloud_to_laserscan` 来自 overlay，ament prefix 为 `sentry_nav/install/pointcloud_to_laserscan`，CMake 源目录为 `sentry_nav/src/pb2025_sentry_nav/pointcloud_to_laserscan`。它与根工作区的同名源码是独立副本，调查时必须核对，不能改错包。

临时诊断仅通过环境变量开启，在同一个转换器内部记录入口精确 TF 查询和输出时间、长间隔时的 Buffer 缓存。限定两轮真实仿真后没有再次出现长等待：

内部日志显示通常在 cloud 到达时源 TF 最新 stamp 还差 1–10 ms，随后即解锁输出。这是正常等待精确采集时刻的 TF，不能因此改为使用最新 TF 或给旧 TF 重盖时间。两轮未再复现不能推翻第 7 节已发生的故障，也不能证明永久根治。

诊断后 cpp/header 已精确恢复原 SHA，主任务随后重建干净库。生产不保留环境诊断代码，不加有限 200 ms TF 等待参数，也不重写 MessageFilter；原因是没有证实其为这次故障的唯一来源。恢复 SHA 核验见 `临时扫描诊断_恢复核验.json`；临时诊断源码只在记录目录留档，不运行。

核对依赖实现时发现的候选仅供后续复发追查：[geometry2 0.25.22 Buffer::waitForTransform](https://raw.githubusercontent.com/ros2/geometry2/0.25.22/tf2_ros/src/buffer.cpp) 先登记转换请求、再登记超时定时器；[CreateTimerROS](https://raw.githubusercontent.com/ros2/geometry2/0.25.22/tf2_ros/src/create_timer_ros.cpp) 原样使用等待 duration。回调先后竞态与默认最大 duration 的数值边界都未在本轮被证实命中，不写成根因。

## 10. 最后单世界补验与活 UDP 取证

旧 `rolling_trial_01` Gazebo server 曾在包装进程退出后残留，属于此前负载/成功率比较的混杂因素。主任务精确核实 partition 后清理，强化只清理本轮所属进程的测试脚本，再执行最后 `rolling_single_world_final`，生产参数不再修改。

该 case 首次路线与重复下发均 SUCCEEDED，835 cloud / 824 scan，scan 最大源年龄 0.074 s、最大到达间隔 0.315 s；cloud→scan 匹配到达中位 1.38 ms、最大 13.36 ms。三层 odom 各 779 条，operational odom 最大到达间隔 0.358 s、最大源年龄 0.112 s，没有 0.8 s 级冻结。云台 TF 源间隔中位与 p99 仍为 0.010 s。

同时已取得真实活进程 UDP 丢包增量：converter 的一个 socket 从 0 到 25，另一 socket 增加 148；sensor_scan_generation socket 增加 388，Point-LIO 增加 53，loam_interface 增加 126。`ss skmem` 实际接收容量为 212992 B。[UDP接收只读核验.md](/home/hui/文档/ChatGPT/导航仿真/路线优化与小电脑部署审计_2026-10-31/UDP接收只读核验.md) 给出范围、完整记录和边界。没有修改系统或 DDS 设置；这些数据证明接收路径有丢包，尚未建立各端口与具体 ROS topic、历史空档的唯一因果关系。

最终结论仍为：本轮已做可验证的积压/陈旧覆盖防护及冗余 TF 限频，并通过最后单世界首次与重复路线；偶发扫描/定位停顿的永久根治尚未完成，应将 UDP 接收丢包、定位点云配对与进程清理可靠性合并作为后续集中处理项。不得回写历史失败为通过。
