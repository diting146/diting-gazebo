# 算法与边界说明

日期：2026-11-01。此文档解释当前源码与算法边界；最终集成后的构建、取消、定位扰动与失败记录见同目录《修改与验收说明.md》。功能集成已验收，不代表长期稳定性验收完成。

## 1. 当前导航链路

当前保留 Nav2 框架：Point-LIO 跟踪运动，small_gicp 与先验点云匹配并提供 map→odom，YAstar 使用 Nav2 代价地图进行全局规划，原 Nav2 局部控制器执行路径，隧道行为树处理洞外准备、底盘对齐、洞内轴线通行和出洞恢复。

本轮增加的轨迹优化位于 **YAstar 搜索之后、普通 Nav2 Path 输出之前**。它没有替换 YAstar 搜索，没有接入 Kinodynamic A*，没有更换局部控制器。现有 Theta* 插件仍可保留，但本轮默认算法是 YAstar。

实现入口：[yastar_planner.cpp](/home/hui/diting-gazebo-feat-sentry-nav-simulation/src/pb2025_sentry_nav/tdt_yastar_planner/src/yastar_planner.cpp)。

## 2. 实际使用的东大轨迹优化代码

原始来源是本机 TDT Nav Kit 的 [minimumSnap.cpp](</home/hui/open source/tdt-nav-kit-main/src/MinimumSnapOsqp/minimumSnap.cpp>)，SHA256 为：

```text
368e220c8cfc4928decd8668c3d09c7bebaf8492b59be134a8337b5f5a56d1c0
```

抽取的是 `MinimumSnap::Backend::Close` 闭式等式约束后端，包括 `unpack`、`validTimes`、`generateQ`、`generateA`、`generateLow`、`generateUp`、`postProcess`、双轴 `closeSolver` 和 `trapezoidalTimeAllocation`。上列 9 个函数体与原文件逐字一致，类名、Item 声明和函数签名类型名作了独立组件所需调整。来源核验见 [提取一致性核验.json](/home/hui/文档/ChatGPT/导航仿真/轨迹优化与定位收尾_2026-11-01/候选/提取一致性核验.json)，原文件清单见 [TDT_EXTRACTION_SHA256.txt](/home/hui/文档/ChatGPT/导航仿真/轨迹优化与定位收尾_2026-11-01/候选/TDT_EXTRACTION_SHA256.txt)。

本次固定使用五次多项式（6 个系数），主要优化三阶导数平方积分，并保留原实现的小幅速度系数正则，因此准确名称为 **闭式 minimum-jerk 几何路径优化**。没有启用四阶导数 minimum snap，也没有接入 OSQP 或 SFC 安全走廊后端。本机已有 Eigen，本次未新增 OSQP 依赖。

原作者注释为 SnifferCaptain，原 MIT 版权所有者为 Rongxuan Ye 和 BoLin Li。实现顶部和包内 [TDT_LICENSE_NOTICE.md](/home/hui/diting-gazebo-feat-sentry-nav-simulation/src/pb2025_sentry_nav/tdt_yastar_planner/TDT_LICENSE_NOTICE.md) 保留许可与来源说明。

项目新增部分是控制点选择、采样、预算、完整车身验证、取消与回退适配；这些适配与原 TDT 求解核心分别说明，没有将自写平滑器冒充原算法。

## 3. 优化能做什么，不能保证什么

优化器尝试把 YAstar 折线中的尖锐转角改成较平滑、位置及前两阶导数连续的曲线，再采样成普通几何路径交给当前控制器。求解时使用的分段时间、首末切向速度和加速度参数用于构造多项式，并未成为控制器必须跟踪的时间表。

因此当前接入可以利用路径形状改善，**不等于具备按时间轨迹跟踪、全程速度/加速度硬约束或最短通行时间保证**。不能仅凭 minimum-jerk 目标宣称车速更高、制动距离更短或真机更安全；这些结论需要控制器和实际运行数据支持。

完整车身检查沿用 YAstar 的实际底盘初始朝向，不把路径切向当成车身朝向，也不新增朝向维度搜索。运动过程中仍由控制器检查碰撞，隧道阶段仍由原行为树管理朝向。

洞内执行路径由 [TunnelPassage::straightPassagePath()](/home/hui/diting-gazebo-feat-sentry-nav-simulation/sentry_nav/src/sentry_tunnel_bt/src/tunnel_passage.cpp:1053) 独立生成；`PLAN_PASSAGE` 确认规划穿越所选隧道后，会将跟踪路径换成该轴线。不能把普通全局优化曲线直接当成最终洞内跟踪曲线。

## 4. 碰撞检查、预算与回退

原 YAstar 路径先使用精确双精度首末坐标完成全车身扫掠验证。优化器随后选择控制点，保留明显角点，沿原折线弧长补点。角点或补点超预算时，跳过优化，不强行删掉拐弯。

候选曲线采样后恢复原始双精度端点，逐点及逐段调用同一张代价地图快照、同一车身朝向的完整扫掠检查。致命障碍、未知格和地图外区域均不可通过。最终输出是经过验证的折线；没有声称未输出的连续多项式在采样点之间具有另一套独立安全证明。

当前默认预算为：

| 项目 | 默认值或限制 |
|---|---:|
| 优化至验证的稳态时钟预算 | 30 ms |
| 控制点上限 | 12，源码允许的硬上限为 24 |
| 输出点上限 | 1200 |
| 控制点补点间距 | 0.6 m |
| 明显角点提取容差 | 0.05 m |
| 输出采样参考间距 | 0.025 m |
| 相对原路径最大点偏离 | 0.25 m |
| 最大路径长度比例 | 原路径的 1.1 倍 |

碰撞、数值异常结果、超时、点数、偏离或长度超限都会明确返回原因，回退到已经验证的原 YAstar 路径，保持原坐标不变。日志区分 `applied`、`body_collision`、`time_budget`、`corner_point_budget` 等，并累计采用与回退次数；日志有节流，不能仅统计日志行数代替实际调用次数。

30 ms 是优化器的合作式预算。单次 Eigen 分解不能被抢占，只能通过控制点上限控制规模，并在返回后丢弃超时结果；包装器最终再次检查路径的耗时也在该预算之外，不能宣传成整个规划请求具有 30 ms 硬实时上限。

插件默认优化开关关闭，当前 LIO 与 Ground Truth 仿真 YAML 显式打开，便于做开关对照。配置入口：[nav2_params_lio.yaml](/home/hui/diting-gazebo-feat-sentry-nav-simulation/sentry_nav/src/sentry_sim_bringup/config/nav2_params_lio.yaml:591)、[nav2_params_ground_truth.yaml](/home/hui/diting-gazebo-feat-sentry-nav-simulation/sentry_nav/src/sentry_sim_bringup/config/nav2_params_ground_truth.yaml:605)。

## 5. 规划取消的范围

本轮提供可选 `CancelablePlanner` 接口，并使用独立 `sentry_planner_server` 接收具体目标的取消信号。未修改系统安装的 Nav2 ABI 或 `/opt/ros`。YAstar 在自身锁和地图锁等待、地图准备、搜索、扫掠检查及几何优化循环中检查该目标是否取消。

优化器返回 `cancelled` 时，必须终止整个规划请求，不能当成普通优化失败后继续返回路径。普通优化失败可以回退，外部取消不可以。

当前目标与 pending 目标分别判断：取消当前目标不应误取消 pending，取消 pending 不应停止当前目标。成功提交与完整的底层取消状态转换使用同一把锁，避免只检查 `is_canceling()` 后又在窄时间窗内提交成功。相关实现和测试位于 [sentry_planner_server](/home/hui/diting-gazebo-feat-sentry-nav-simulation/src/pb2025_sentry_nav/sentry_planner_server/README.md)。最终实际 action 验收结果以主验收报告为准。

没有实现上述扩展的标准规划器插件仍可使用原 `createPlan(start, goal)`，服务器在调用前后检查取消；无法在普通插件内部抢占它正在执行的计算。YAstar 的单次 Eigen 求解同样具有前述不可抢占限制。

## 6. 人工摆放、可信定位与实际出生点

第一版限定在约定出生区域附近摆放，修正位置、朝向误差，不增加全场自动重定位。`spawn_x/y/z/yaw` 只用于 Gazebo 模型出生，`initial_pose_x/y/z/yaw` 独立表示地图下 base_footprint 的定位初猜，不能用仿真真值替代真机定位。

初始化在点云对应时间查询变换，计算：

```text
T_map_odom = T_map_base × T_base_odom
```

地图匹配成功后，Nav2 从实际地图位姿规划到固定三个途径点；三个点本身仍在地图坐标中，不随着出生点平移。位置变到隧道另一侧时，当前固定路线不会自动交换入口或点序。

small_gicp 发布 `localization_status`，综合收敛、有限数值、内点数、内点比例、协方差加权误差和单次修正量，并要求连续健康匹配后才标记可信。误差指标不是米制 RMSE，这些阈值属于本场景待标定参数；连续匹配也不能证明全局位置唯一正确，仍须做独立出生偏差验证。配准失败、输入过期、手动初值重置、源时间或时钟回退会撤销可信状态。

LIO 模式的 `startup_navigation` 除原 lifecycle、odom、scan、TF 和 action 条件外，还检查可信状态的源时间及墙钟接收时间新鲜度，全部条件连续稳定约 3 秒后才发送固定路线。GT 不依赖 GICP 状态，建图模式不创建该任务。

**该门控只限制启动节点发送的固定路线。** 直接通过 RViz 或其他 action 客户端发布目标不会自动经过这个门控，当前也没有新增运行中定位异常强制停车功能。不能把该状态显示成所有导航入口都有定位保护。

`route_status.home_pose` 记录第一次完成全部就绪检查、准备发送任务时的实际 map/chassis 位姿。重复 `start_route` 不覆盖，时间回退时清除。它仅是本进程状态记录，不落盘，不发布返航目标，没有实现没血返航、定时再次出发或裁判任务逻辑。

## 7. 已有路线对照结果及不能下的结论

下表来自本轮已有 `run_result.json`；这些试验发生在最终定位与取消全部集成验收之前，不能替代最终版本验收。

| 记录 | 优化开关 | 实际结果 |
|---|---|---|
| `baseline_route` | 关闭 | 首次路线与重复路线均为状态 4：SUCCEEDED |
| `optimized_route` | 打开 | 首次路线状态 6：ABORTED；洞内横向偏差触发保护，后续重复路线未完成 |
| `optimized_retry` | 打开，未因上次失败改变配置 | 首次路线与重复路线均为状态 4：SUCCEEDED |

首次失败在模拟时间约 21.937 s 触发 `tunnel_heading_or_centerline_deviation`。当时 map 位姿 y≈3.4398，中心线 y=3.475，偏差超过 0.035 m；仿真实际 y≈3.4684，车头偏差较小。记录显示存在厘米级定位差异，扫描与定位输入没有在该段超时，洞内仍执行独立轴线。没有证据支持把这次失败简单归因于优化曲线切弯，也没有为通过而放宽洞内守卫。

保持配置的复测两次成功，证明新增几何优化有实际采用且能够完成路线；它不能抹掉首次失败。样本数量少，首轮/重复路线的起点和准备过程也不同，**当前不能宣称轨迹优化提高了成功率或降低了整条路线耗时**。
